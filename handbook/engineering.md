# CutsetのAI駆動開発

一つの変更は、編集者の操作と観測できる結果で説明する。「間を残す」を選んだら原音の同じ区間を聞ける、確定前に閉じたら元のタイムラインへ戻る、といった約束を最初に置く。実装・テストが食い違ったとき、編集者に約束した動作からどちらを直すか判断できるようにする。

## 一つの作業を渡す

計画担当は次の短い作業票を作る。既に製品仕様にある条件は参照先を示す。次の担当は差分と作業票だけで再開できる。

| 作業票 | 記入する内容 |
| --- | --- |
| 目的と参照 | 編集者の操作を一つ選ぶ。該当仕様、上流の既存命令、変更元コミットを記録する。 |
| 受入例 | 入力素材・編集前の状態・操作・観測値。成功例に加え、たとえば対象のロックや古い候補を与えたときの期待値を書く。 |
| 所有範囲 | 触るファイルと担当、同時に触ると衝突する共有点、必要な前段の出力を示す。 |
| 検証と終了 | 実行するコマンド、比較するフレームまたは音の範囲、手で確かめる感触を決める。仕様判断が必要な点は保留欄に置く。 |

1. **実装担当**は機能ブランチで再現ケースを作る。既存テストで不足する挙動なら、修正前の失敗を確かめてから最小の変更を入れる。上流取り込みや衝突の解決も実装側で行う。
2. **独立した確認担当**は別のエージェントまたは開発者が担う。対象コミットの差分を読み、危うい条件を一つ選び、専用の案件コピーで崩してみる。指摘には入力・再現操作・実害・期待値を添え、修正は実装担当に返す。文書だけの変更では別の読者がリンクと手順を照合する。
3. **取りまとめ担当**は確認対象のコミットと採用候補のコミットを照合する。修正や上流統合で版が変わったら、変わった範囲を再確認する。編集者が音を聞いて決める採否、公開配布の判断、基準値の改訂はそれぞれの担当者が記録する。

並行してよいのは書き込み先が別で、相手の未完成の出力にも依存しない作業。エンジン命令の契約を変えるときは先にその入出力を固め、UIとCLIの検証をその後に分担する。

## 実装の判断

| 観点 | Cutsetでの判断例 |
| --- | --- |
| 名前と責務が読めるか | UIは候補の表示・試聴を扱い、エンジンが確定時の編集と履歴を管理する。 |
| 規則の所有者は一つか | トラックのロックとUndoの判定を、手操作・AI・CLIから同じ編集命令で通す。 |
| 経路を短くできるか | 新しいプロジェクト形式やラッパーを増やす前に、既存の配置IDとコマンドで表せるか調べる。 |
| 編集者の待ち時間はどう変わるか | 同一素材・同一端末で、操作から音や画が返るまでを前後比較する。条件と数字を一緒に残す。 |
| 運用と保守の負担はどう変わるか | 反復は影響するcrateから試す。繰り返すミスは小さな回帰ケースや機械検査へ戻す。 |

## 検証の記録

編集モデルと時間計算を触る場合、作業コピーのルートで次を実行する。範囲がUI、保存、出力に及べば対応するcrate・実案件コピーの経路も追加する。統合の節目には上流の全体ゲートと必要な外部参照をローカルで実行する。[テストの対象と前提](../docs/testing.md)

```sh
git rev-parse HEAD
git status --short
cargo fmt --all -- --check
cargo test --locked -p filmcraft-time -p filmcraft-edit
```

記録には **対象SHA、作業ツリーの状態、入力、実行コマンド、終了コード、観測値、未確認の項目** を含める。未コミット差分を含む実行結果はその旨を明記する。たとえば64秒の初期案件では「1,600フレームを読み戻せた」と「編集者が間を選んで60秒に仕上げた」を別々に記録する。画や音を変えたら保存した案件を別プロセスで開き直し、書き出したファイルでも該当箇所を確かめる。

仕様に答えがある判断は担当者が進める。素材の利用許諾、外部推論への送信、編集者が残す呼吸の判断など、手元の証拠で決められない点は「何を誰が決めれば再開できるか」を残す。待つ間は公開可能な合成素材、固定候補、手元で確認できるテストを進める。公開用の記録には再現できる合成入力と結果だけを載せる。

## main と上流の更新

Cutsetの統合先は個人forkの `origin/main`。本家は `upstream/main` で参照する。上流を更新するときは最新の両方をfetchし、Cutsetのmainから作業ブランチを切って上流をマージする。仕様グラフの影響範囲、編集試験、公開素材と秘密情報をローカル確認してから統合する。GitHub Actionsは停止を継続する。機能の受入条件と進捗は[仕様](../spec/README.md)・[マイルストーン](../spec/milestones.md)・[検証ループ](../spec/harness.md)で共有する。

同じ条件で3回失敗したら、作業台の再開メモに失敗条件・確認済みの原因・解除に必要な入力を残し、その周回での自動再試行を止める。独立して検証可能な次の作業へ移る。検証担当、レビュー担当、編集者の採否を記録し、固定評価やリリースへの昇格には担当者の判断を残す。
