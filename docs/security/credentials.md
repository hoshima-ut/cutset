# 認証情報を公開しないための開発手順

## 最初に設定する

ローカルではGitに書き込む内容を検査し、リモートではGitHubのSecret scanningとリポジトリのPush protectionを使う。GitHub Actionsを停止した状態で両方を利用できる。MacでGitleaksが未導入なら `brew install gitleaks` で導入する。開発者用の確認はリポジトリ直下で実行する。

```sh
gitleaks version
tools/install-hooks
tools/secret-guard staged
python3 tools/test-secret-guard.py
```

新しいクローンごとにインストーラを実行する。既に独自フックを使っている開発者はその設定を残し、両方の検査をつなげる。コミットとpushの検査は異なる。後のコミットで削除した値も、送る履歴に含まれていれば第三者が読める。

インストーラはこのクローンのGit管理領域に検査器のスナップショットを保持する。ブランチを切り替えたときも検査が残る。フックを変更した差分は別の担当者が確認してから、`tools/install-hooks` を再実行して更新する。作業コピーを別の場所に移すと保存した絶対パスが古くなる。移動後は作業を再開する前に `git config --get core.hooksPath` の実体を確認し、このクローン用にフックを再設定する。

ステージ検査はファイルの作業中の内容ではなく、コミットに入るGitオブジェクトに対して行う。push前には宛先に増える履歴とタグを調べる。既知の認証ファイル名や秘密値のパターンを検出すると停止する。検査できないLFSポインタも停止対象。上流FilmCraftを取り込むときは、[公開済みの上流の一覧](../../tools/public-sources.txt)にあるリポジトリが実際に公開しているコミットと、その内容と同じファイルは再検査しない。宛先と上流には直接問い合わせ、手元のremote設定やGit設定は信用しない。取り込みで解消した競合やCutset側の変更は従来どおり検査する。一覧には公開を確認したリポジトリだけを載せる。データセットや動画はパイロット手順で `target/` に生成する。エラー調査は `git status --short` や `git log --oneline` から範囲を絞り、実値や生ログを外に貼らない。

## 何を守るか

- モデルや配信サービスのAPIキー、GitHubのトークン、署名鍵、MCPの制御トークンをGitで管理しない。共有する設定例には空の環境変数名を使う。検出時の記録は検査名・規則・件数と対処だけにする。
- 将来の公式AIプラグインでは認証情報をホストが管理する。デスクトップではOSの資格情報ストア、開発中はプロセスに限定した値を使う。ブラウザに配るWasm/JSへ共有サービスのキーを組み込まない。プロジェクトファイル・プロンプト・モデルに渡す設定・MCP応答・クラッシュログ・画面収録にはキーを含めない。
- PR、Issue、AIとの会話への貼り付けや、リリースに手で添付するバイナリはGitフックを通らない。診断情報を外に渡すときは許可した項目だけ取り出す。未知の形式や画像に写ったキーの発見は保証できない。試験には合成データを使う。
- GitHub側では **Settings → Code security** でSecret scanningとPush protectionを確認する。Push protectionで止まった変更は履歴から取り除いてやり直す。管理者が設定を変えられることや検出パターンの対象範囲も踏まえ、公開の判断をスキャンだけに委ねない。[GitHubのPush protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)

## 検出したとき

送信前に止まったら対象をステージから外し、秘密を含まない設定方法に直す。過去コミットが対象なら公開前の作業ブランチの履歴を点検する。実値を端末ログやチケットに貼らない。外部に出た可能性がある実キーは発行元で直ちに失効・再発行し、利用履歴を確認する。その後に履歴・添付・キャッシュを関係者と整理する。[報告窓口](../SECURITY.md)
